# Limitations, expected encounters and closure work

This inventory accompanies the [closure plan](completion_plan.md). It explains
what users will encounter and why; it is not a declaration that closure has
already been achieved. Generic computation remains required. A failed proof or
specialized pattern is a reason to try broader standard MLIR with explicit
storage/effects, not to erase the computation or label it GPU-specific.

The [tracked generic-gap reproducers](../tests/data/v1_generic_gaps.json) retain
exact source, requested bindings, the native verifier pin and observed refusals.
They are open computation gaps and independently block the release checker.
The [completed admission review](semantic_profiles.md) froze five named generic
work items with eight exact source witnesses and bounded attempts. Low-precision
printing, unpacked i4 storage and FP8 arithmetic/accumulators are qualified;
FP8 atomic addition qualifies eight public programs; entry value ports qualify
nineteen more, including both original entry witnesses. All five original items
are focused-qualified. The additional native-valid `noinline` helper finding is also focused-qualified;
its original call intent and changed performance boundary remain explicit.
Completing that review does not establish final execution qualification.

## Hardware or unavailable-source semantics

| Limitation | Why a kernel might use it / when it appears | Why portable lowering cannot infer it | Current remedy |
| --- | --- | --- | --- |
| Arbitrary inline assembly | Hand-tuned attention/GEMM, packed arithmetic, special instructions, approximate math and device diagnostics. | Assembly text can observe physical state or have undocumented value/effect semantics; a purity label is insufficient. | Default intake refuses with source location. Existing optional qualified integer providers remain available. Supply a typed semantic implementation or use ordinary Triton operations. Assembly coverage is not required for generic-op closure. |
| Physical addresses, clocks and hardware identities | Pointer tagging, device allocators, alignment tricks, clock-based profiling and lane/core-specific algorithms. | Logical tensor roots and iteration coordinates do not define a numeric GPU address, timer or physical participant identity. | Preserve logical pointer offsets/round-trips where proved. Escaping physical observations require an explicit backend contract or remain unsupported. Do not invent addresses or clocks. |
| Post-layout GPU operations and physical descriptor bytes | Saved backend IR, warp-specialized kernels, architecture-selected layouts and DMA descriptors. | These encode a particular device's storage/participation rules rather than pre-layout tensor computation. | Capture earlier TTIR and use logical descriptors. Physical descriptor/runtime implementations belong in target support. This frontend does not decompile GPU binaries. |
| General cross-program/external synchronization and async completion | Producer/consumer pipelines, inter-CTA queues, device/host publication and asynchronous shared-memory staging. | Serializing a launch or dropping a wait can change permitted observations, ordering and lifetime. The existing invocation-local profile does not define arbitrary external participants. | Qualified local phases/effects remain supported. A synchronous portable expansion needs a real equivalence/dependency argument. Otherwise require an explicit execution provider and report backend-required. |
| Unknown external function implementation | Vendor device libraries, custom approximate math and private helper libraries. | A function name/prototype does not define its arithmetic, rounding or side effects. | Existing qualified external math profiles work. Supply a typed implementation/effect contract; unspecified external semantics cannot count as portable support. The generic call operation itself is not being discarded. |
| Exact agreement with every GPU arithmetic mode | Tensor-core precision modes, FTZ/subnormal behavior, packed low-precision formats and approximate device functions. | Different selected source/backend numeric policies can produce different words. Tolerances or provenance cannot silently grant a changed policy. | Select an implemented named numeric profile and expose differences. A missing generic arithmetic implementation remains work; unspecified hardware behavior needs an explicit contract. |

Cache hints, physical coalescing and placement choices may become provenance
when they do not affect values/effects. Logical tiles, loaded-value reuse,
accumulation order, masks and dependencies remain executable. A generic load
fallback must keep its actual root, indices, guard, fill and source ordering.

## Current product boundaries

| Boundary | When it comes up | Current state / next action |
| --- | --- | --- |
| Automatic launch discovery | A PyTorch `triton_op` wrapper launches several kernels, performs surrounding arithmetic, uses views/mutation, symbolic grids, autotuning or hidden scratch. | The new automatic adapter currently covers static pure single-launch wrappers with fresh returned outputs. It rejects unaccounted wrapper work. Existing explicit model/storage bindings cover additional cases; broader automatic wrapper composition remains open. |
| Coupled/asymmetric packed map grouping | A `tt.map_elementwise` body combines different packed slots or computes different functions for each slot. | Pre-layout TTIR does not uniquely determine which logical coordinates share per-thread registers. Supply the existing explicit `source_layout` semantic specialization; the qualified grouping adapter emits standard tensor/SCF/Linalg and records the source coordinate map. The consumer remains free to choose its own hardware mapping. Without this source information, refuse rather than assume neighboring tensor elements. See [the grouping contract](source_grouping.md). |
| Source/version compatibility | A model uses a different Torch/Triton release or saved IR from another compiler pipeline. | The TTIR frontend is pinned to Triton 3.7.1. Automatic discovery probes Torch 2.10 and records its separate source-capture version boundary. New versions need compatibility qualification rather than silent parsing. |
| Entry and helper calling convention | Hand-authored/imported TTIR exposes by-value entry results, multiple public entry functions or helpers that the supported normalization cannot inline. | Intake requires one declared kernel entry with explicit logical buffers/scalars/state/results. Numeric value arguments/returns now use qualified v3 storage ports. Multiple public library APIs require per-entry modules; recursive/uninlineable control still needs accepted source normalization or an explicit implementation. A native-valid noinline helper is separately tracked below. Provenance supplies no omitted body or calling convention. |
| Public physical alias/copyback | Callers expect Python-visible mutation, overlapping storage identity or shared external memory. | Functional state/results and selected explicit storage adapters exist. Unimplemented physical invocation behavior must be requested explicitly; returning a changed tensor does not imply caller copyback. |
| Generic address/shape/ownership compositions | Loaded/nonlinear indices, selected roots, changing loop-carried storage, value-sized intermediates and unusual valid control-flow combinations. | Many qualified paths exist, but universal composition closure has not been established. Use checked roots/extents/shape/scalar bindings and generic logical memory/control expansions; remaining valid generic failures are release blockers, not hardware exclusions. |
| Integer atomic storage boundary | Low-precision counters/state in hand-authored or imported TTIR; higher-level Triton APIs may restrict or promote widths. | i1/i4/i8/i16/i32/i64 RMW/CAS retain source-width updates and all old/final words; f16 and ordered byte-backed i16 views also qualify. Public i4 uses the explicit unpacked contract below; no wider-final-cast approximation is used. See [atomic memory](atomic_memory.md#byte-sized-integer-source-words). |
| Packed low-bit state | Two counters per byte or other coupled bit storage in imported/hand-authored TTIR. | Public i4 now qualifies through both result ABIs as one canonical uint8 cell per value, restricted to 0..15; invalid padding fails before invocation. This cannot represent paired nibbles sharing a physical byte or infer their atomic participation. Supply actual i8 storage and source unpack/update semantics, retaining shared-byte effects and disclosing representation/performance changes. By-value i4 scalars remain a separate entry-binding gap. See [the carrier contract](atomic_memory.md#unpacked-four-bit-integer-cells). |
| FP8 arithmetic and accumulators | Quantization math, numeric maps/reductions and scaled dots with FP8 C/results; Python kernels often promote these values to f16/f32. | All four formats now qualify through thirteen public programs using f64 native emulation, exact FP8 result casts and word-preserving sign operations. Portable MLIR retains its types, tiling/control, original C and each rounding boundary. This host software expansion can cost more instructions than device FP8 arithmetic and does not supply arbitrary GPU precision/FTZ or performance equivalence. FP8 atomic addition remains separate. See [the numeric scope](fp8_arithmetic.md). |
| FP8 atomic addition | Custom low-precision accumulators/state; ordinary kernels frequently choose f16/f32 state instead. | All four formats now have a [qualified per-update numeric and byte-CAS route](fp8_atomics.md), retaining original old words and rounding after every update. Eight public programs qualify all operand pairs, source masks/orders/scopes, constant zero forms and both result ABIs. The scalar f64/CAS fallback can cost throughput under contention; it supplies no external publication or GPU execution-order equivalence. Wider-state source code changes precision/storage and remains an explicitly declared alternative. |
| Low-precision diagnostic profile | Debugging internal i4 arithmetic or FP8 tensor values/packing. | All six integer widths and all eight floating formats now have a logical formatter. Four public programs qualify FP8/i4 exact streams and words; FNUZ's unique unsigned NaN prints `nan`. Physical device printf scheduling/varargs remains separate. Printing itself adds no tensor ABI or general FP8 arithmetic. |
| Public entry values | Selecting a returning helper as a standalone TTIR entry, or importing by-value f16/BF16/FP8/i4 inputs. | Explicit [v3 value/result ports](entry_values.md) now implement this route for every admitted numeric scalar/static-tile type. Original helpers and bodies inline before memory analysis; native/public tests retain exact words, all results, source control and logical grids. Value inputs, result ports and mutable pointer state need separate roots; scalars use one-cell/per-program tensors. Raw pointer/descriptor objects need actual logical root/offset/field wrappers. No low-precision native by-value ABI is inferred. |
| Private `noinline` helpers | Real JIT helpers use call grouping to control code size and register pressure. | [Defined bodies now use the existing upstream inliner](call_intent.md), retaining actual computation/effects and original Boolean grouping intent in provenance. Five public programs and eighteen invocations qualify the correction. Physical call boundaries, code size and register pressure may change; downstream outlining requires its own legality checks. Missing bodies, external semantics and recursive/uninlineable forms still need an actual implementation. |
| Additional integer word views | Kernels reinterpret BF16/FP8 storage for integer counters, comparisons or float min/max implementations. | Direct floating exchange now qualifies on all pinned formats, including exact NaN bits. Automatic integer RMW/CAS through BF16/FP8 owning roots remains outside the current word-view profile; checked raw owning-allocation bindings may apply. Broader automatic views still need source/profile qualification. This is a generic storage/interface boundary, not an architecture-specific instruction. |
| Packet-sharing experiment | Optional narrow integer assembly inside a dynamic recurrence. | The packet-preserving experiment exposed a lifetime-proof failure and is retained as an ignored patch, outside the active frontend. The qualified scalar word recipe declares its sharing loss in `packet_execution` provenance. No lifetime check is bypassed. This optional assembly optimization is distinct from generic-op support. |
| Demo breadth | Training, dropout, multi-head/causal attention, large models or arbitrary dynamic sequence lengths. | The delivered demo source is two complete small single-head pre-norm inference blocks with ReLU FFNs and no dropout/causal mask. It demonstrates automatic integration and correct computation, not those unmeasured model configurations or performance. |
| Target execution/performance | A user expects an accelerator executable or the GPU kernel's throughput. | Native and public Merlin host execution plus selected serial images establish their own scope. Accelerator scheduling, resources, runtime ABI, correctness and timing need separate target qualification. Portable MLIR success is not a speedup claim. |
| Separately selected stock CLI compiler transport | Operators select Merlin's Python-free `stock-cli` driver instead of the qualified public Python host path. | The signaling-NaN min/max correction currently finalizes the Python runner's retained/translated LLVM. Its 12-case scalar qualification does not establish stock CLI equivalence; that driver needs its own legalization/evidence. This is a consumer transport boundary, not an excluded generic TTIR operation. |

The final closure report must retain this distinction: hardware exclusions,
missing user/source contracts, automatic-adapter limits, and unfinished generic
implementation are different outcomes. None becomes a successful portable
lowering merely because a diagnostic or provenance record exists.
